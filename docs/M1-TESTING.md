# M1 全量回归清单

> 适用版本：v1.2-M2（M1 能力在 M2 之后仍全部有效）
> 使用方式：逐条执行并在通过后勾选 `- [ ]` → `- [x]`。
> 环境标记：🟢 本地（DevTools 造数即可） · 🔵 真实 Supabase（需登录真实账号） · ⚠️ 破坏性（先导出备份）
> 每条格式：操作（含造数）→ 预期。

## 一、准备（每次全量回归先做）🟢

- [ ] **1. 环境与入口**
  操作：`npm install` → `npm run dev`，打开 `http://localhost:5173`；依次访问 `#/todos`、`#/goals`、`#/habits`、`#/settings`；DevTools → Application → Local Storage 查看 key。
  预期：四个入口均能渲染，Console 无红色报错（HashRouter，地址必须是 `#/xxx`）；localStorage key 前缀为 `planner:`，值形如 `{"v":1,"data":...}`；`index.html` 引用 `/src/main.tsx`，`src/main.tsx` 挂载 `ThemeProvider → AuthProvider → DataProvider → App`，`ROUTE_DEFS` 路由齐全。

- [ ] **2. 破坏性测试前备份**
  操作：设置 → 数据管理 → 导出备份；或在 DevTools 清空 Local Storage；若刚跑过 `npm run build`，先在 Application → Service Workers 注销并 Hard Reload。
  预期：得到 `planner-YYYY-MM-DD.json`；清空后需重新登录；不因 PWA 缓存旧 bundle 出现“改了没生效”的假象。

## 二、新老数据迁移 🟢

- [ ] **1. 旧 JSON 导入不白屏 + `priority → quadrant`**
  操作：新建 `legacy.json`（扁平结构，含 `todos`：`{"id":"legacy-t1","title":"旧任务-优先级字段","priority":"q1","date":"2026-11-14","listId":"legacy-list","categoryId":"legacy-cat","completed":false}`、`{"id":"legacy-t2","title":"缺字段任务"}`、`{"id":"legacy-t3","title":"非法优先级","priority":"high","due_date":"2026-11-14"}`，以及 `lists`、`categories`、`financeCategories`、`goals`、`quotes`、`themes`）；设置 → 数据管理 → 导入数据 → 选择该文件（无二次确认，选中即导入）。
  预期：① 弹出「导入成功，数据已自动兼容校验」，不白屏、无红色报错，原始 JSON 写入 `planner:backup:raw-last-import`；② `#/todos` 切到 `2026-11-14` 可见「旧任务-优先级字段」，象限为「重要且紧急」，`legacy-t3` 因 `priority` 非法回落「重要不紧急」；③ 看板四列可见，`legacy-t1` 在第一列；④ 再导出备份，`todos` 中只有 `quadrant`，不再有 `priority`。

- [ ] **2. 旧 `lists / categories / financeCategories` 映射**
  操作：导入上方 `legacy.json` 后进入 `#/todos` 查看左侧「我的清单 / 任务分类」，再进 `#/finance` 查看分类下拉。
  预期：① 侧栏「我的清单」下出现 `📁 旧清单`，点击只筛出 `legacy-t1`；② 待办行显示清单标签「旧清单」、分类标签「旧分类」；③ 记账分类下拉包含「旧记账分类」且类型为支出；④ 旧文件使用 `listId/categoryId` 驼峰时，导入后仍正确落到 `list_id/category_id`。

- [ ] **3. 缺字段兜底**
  操作：`legacy-t2` 只有 `id` 与 `title`；导入后打开左侧「🗂️ 未排期」，再点「添加待办」新建一条。
  预期：① `legacy-t2` 出现在「未排期」（无 `due_date`），标题正常、不崩溃；② 新待办默认落在「收集箱 / 重要不紧急」，保存后刷新仍在；③ 13 域缺失的域用种子补齐（清单含 `inbox`，分类含 c1–c5，记账分类含 fc1–fc6 / fi1–fi4）。

- [ ] **4. 旧目标 `period_key` 补全**
  操作：导入 `legacy-g1`（`type:"yearly"`、`start_date:"2026-03-05"`、无 `period_key`）；打开 `#/goals` 选「年度目标」，点「回到今天」。
  预期：出现「旧目标」，周期标签为 `2026 年`（由 `start_date` 推导，不落在当前月/周），进度 40%；再导出 JSON，`period_key` 已写为 `"2026"`。

- [ ] **5. 导入 `quotes` 后内存即时刷新**
  操作：导入含 1 条 `quotes`（id `legacy-q1`）的 `legacy.json` 后**不刷新**，直接回 `#/` 首页点「换一条」，直到出现导入的句子。
  预期：① 无需二次刷新即可看到「这条来自导入文件」；② `planner:p_quotes` 等于导入文件的 quotes 列表（覆盖语义，不会合并回内置 42 条）；③ 重新加载后仍是这 1 条，`planner:p_quotes_seeded=v1` 已存在，seed 不回灌；④ 导入文件不含 `quotes` 时，原有词库保持不变、不被清空。

- [ ] **6. 导入后刷新仍正确**
  操作：完成本组 1–4 后 F5。
  预期：待办、清单、分类、目标、记账分类全部保持；`planner:backup:raw-last-import` 仍是导入时的原始 JSON；无「导入失败」提示。

## 三、断网 / 云端空 / 冲突拦截 🔵

> 判定逻辑在 `src/core/cloudSync.ts`（`decideCloudAction`），UI 在 `src/app/CloudSyncGate.tsx`。Supabase 需已建好 13 张表且 RLS 允许当前用户读写。

- [ ] **1. 分支 A：读取失败**
  操作：用 SQL Editor 执行 `revoke select on all tables in schema public from authenticated;`（或 Dashboard 临时禁用某张表的 SELECT 策略），或 DevTools → Network 勾选 Offline（先断网再点右上角「重试」）；已登录状态下刷新页面。
  预期：① 弹窗标题「无法读取云端数据」，文案明确「本机数据一条都没有改动」；② 部分表失败时列出失败表名（如 `todos、habits`）；③ 提供「继续使用本地数据」「重试」两个按钮；④ 本地待办条数不变，Console 有错误但不白屏。恢复权限/网络后点「重试」回到正常分支。

- [ ] **2. 分支 B：云端只有种子 / 云端空**
  操作：云端只保留 `todo_lists` 的 `inbox` 与 `categories` 的 c1–c5、`finance_categories` 的 fc1–fc6 / fi1–fi4，其余表清空；本地新标签页在 `#/todos` 建 2 条待办；登录同一账号。
  预期：① 弹窗标题「云端暂无数据，本机有数据」，显示本机各域条数；② 按钮为「暂不上传」「📤 上传本地数据」；③ 点「暂不上传」弹窗关闭、数据保留，退出再登录仍会提醒（`planner:cloud:last-sync` 未写入）；④ 本地空 + 云端空时登录不弹任何窗。

- [ ] **3. 分支 C：云端有、本地空（静默拉取）**
  操作：浏览器 A 登录并按上一分支上传数据成功；浏览器 B 用隐身窗口登录同一账号，等待 2 秒后打开 `#/todos`。
  预期：不弹窗，B 直接显示 A 上传的待办；B 的 `planner:p_todos` 已有云端数据，`planner:auth:owner` 为你的 userId；导出 B 的备份，条数与 A 一致。

- [ ] **4. 分支 D：两边都有（冲突）**
  操作：A 登录并上传 → A 退出登录（自动恢复登录前快照）→ 本地 `#/todos` 新增一条「A本地新增」并删除一条原有待办 → 重新登录 A。
  预期：① 标题「云端与本机都有数据」；② 显示「云端合计 / 合并后将新增 / 将用云端覆盖 / 仅本机保留」四个数字，后两者中「合并后将新增」与「仅本机保留」均 ≥1；③ 三个操作「稍后」「用本机覆盖云端」「以云端为准合并」；④ 点「以云端为准合并」后本地同时出现「A本地新增」与被删掉的那条（同 id 以云端为准，仅本机保留，仅云端补进），且不自动上传；⑤ 点「稍后」数据不变，刷新或重新登录仍会再次提示。若两边 id 集合完全一致会走静默分支，务必先造出新增/删除差异。

- [ ] **5. OVERWRITE 保护 + 上传前快照 ⚠️**
  操作：在冲突弹窗点「用本机覆盖云端」，依次验证倒计时、输入确认词、取消、确认；再单独复测「快照失败中止」。
  预期：① 出现红框「危险操作：用本机覆盖云端」，说明会强制创建云端快照、失败则中止；② 确认按钮初始 disabled，文案 `确认覆盖（3s）`；③ 输入 `overwrite`（不区分大小写）按钮立即可用，或等 3 秒倒计时结束自动可用（此时输入框禁用）；④ 点「取消」红框消失、云端未动；⑤ 点「确认覆盖」成功后云端 = 本机数据，`planner:backup:cloud-before-overwrite` 含 `savedAt / reason:"manual-overwrite" / complete:true / failedTables:[] / tables`；⑥ 先 `revoke select on table time_blocks from authenticated;` 再确认覆盖，出现「云端快照不完整（失败表：time_blocks），已中止覆盖操作」，云端与本地均未被覆盖。

- [ ] **6. 上传前快照（「上传本地数据」路径）**
  操作：先删除 `planner:backup:cloud-before-overwrite`，云端清空、本地有数据；登录 → 弹「云端暂无数据」→ 点「📤 上传本地数据」。
  预期：上传成功后该备份 key 重新出现，内容为上传前的云端（空表）快照；Console 出现 `[上传] ✓ 云端快照已写入本地备份`。

- [ ] **7. 同签名不重复弹窗**
  操作：完成一次「以云端为准合并」或上传后，不退出登录直接刷新页面；再退出并重新登录。
  预期：不退出时 `planner:cloud:last-sync` 记录 `{userId, cloudSignature}`，同一份云端签名再判定不弹窗；退出登录会清除该 key，重新登录必然重新判定（可能再次提示，属刻意行为）。

- [ ] **8. 两边 id 集合完全一致（静默拉取）**
  操作：在分支 C 拉取成功后，用 Supabase Dashboard 只改云端某条待办的 `title`（不改 id、不增删行）；退出后重新登录（或清 `planner:cloud:last-sync` 后刷新）。
  预期：不弹冲突窗，直接拉取（`source='identical-ids'`），本地标题被云端覆盖；若仅本机多一条或云端多一条，则回到冲突分支。

## 四、待办三视图与未排期 🟢

- [ ] **1. 严格日期过滤**
  操作：`#/todos` 选今天，新建 A（今天）、B（日期改为明天）、C（在「未排期」里新建，无日期）；日期切到今天 / 明天 / 后天。
  预期：今天只显示 A，明天只显示 B，后天为空并显示空态；无日期的 C 在任何日期视图都不出现（严格 `due_date === date`）。

- [ ] **2. 未排期入口**
  操作：点左侧「🗂️ 未排期 (n)」。
  预期：顶部出现橙色提示条「未排期：仅显示没有日期的待办……」，右侧有「返回日期视图」；只显示无日期任务，计数 `n` 与实际一致；新添加的待办保持无日期（不自动落到今天）。

- [ ] **3. 逐条补日期 / 批量补日期**
  操作：未排期视图某行右侧日期框选 `2026-11-20`；再点「批量」勾选剩余 2 条 → 选日期 → 「批量补日期」。
  预期：行从列表消失、`未排期 (n)` 递减；切到 `2026-11-20` 能看到这些任务；批量操作后自动退出批量模式并清空选中。

- [ ] **4. 三视图口径差异**
  操作：同一日期建 4 条：Q1 无时间、Q2 `due_time=09:00`、Q3 `due_time=14:30`、Q4 已完成；另用 DevTools 给某条 todo 加 `"start":"08:00"`；依次点「列表 / 看板 / 时间线」。
  预期：① 列表：未完成在前、已完成置底，未完成中置顶优先、有时间按时间升序、无时间排后，默认「按状态」分组计数正确；② 看板：固定四列且空列显示「暂无任务」，每条只出现在自己的象限，点击卡片按 q1→q2→q3→q4→q1 循环移动，移动后列表/看板同步；③ 时间线：只收 `due_time` 或 `start/end` 有值的待办（本造数为 08:00、09:00、14:30），按时间升序排列，Q1 不出现，`start+end` 显示 `08:00 – 09:00`、仅 `start` 显示 `08:00 起`，无时间项时显示「这一天没有带具体时间的待办」；三视图切换不丢数据、不报错。

- [ ] **5. 置顶**
  操作：列表视图中点某条未完成任务的「置顶」，刷新后复查。
  预期：该条移到未完成组最上方并出现 📌，按钮变为「取消置顶」，刷新后仍置顶；已完成任务即使置顶也排在未完成之后。

- [ ] **6. 分组折叠与记忆**
  操作：分组切「按清单」→ 折叠「📁 旧清单」→ 切「按分类」→ 再切回「按清单」。
  预期：折叠状态按 `groupBy:groupKey` 精确记忆，切回后仍折叠；箭头方向同步旋转。

- [ ] **7. 批量选择与全选三态**
  操作：同一天 ≥3 条待办、分组「按状态」；点「批量」→ 勾选组内 1 条观察组头复选框 → 再勾选其余 → 点「全选当前筛选」；再切到看板/时间线。
  预期：组头复选框 0 条为未勾选、部分选中为 indeterminate（横杠）、全选为勾选；点组头只影响本组可见项；顶部显示「已选 x / y 项」并随勾选变化；「清空选择」归零，「全选当前筛选」选中当前日期+清单过滤后的全部项；切到看板/时间线后批量按钮消失、批量模式退出、选中清空。

- [ ] **8. 批量删除**
  操作：批量选中 2 条 → 「批量删除」→ 确认。
  预期：弹出「删除选中的 2 项待办？」；确认后两条消失，`planner:p_todos` 只写一次，页面不闪。

- [ ] **9. 清单 CRUD 与删除联动**
  操作：左侧「管理清单」→ 新建「测试清单」（名称/颜色/图标）→ 重名再建一次 → 编辑改名 → 删除一个有 3 条待办的清单。
  预期：① 新建成功出现在侧栏且颜色图标生效；② 重名提示「已存在同名清单」，不创建；③ 空名提示「请输入清单名称」；④ 删除确认文案为「清单「测试清单」下有 3 项待办，删除后这些待办会移入「收集箱」。确定删除该清单？」，确认后清单消失、原待办 `list_id` 变为 `inbox` 并在「收集箱」可见；⑤ 「收集箱」可改名、可编辑颜色图标，删除按钮 disabled 且提示「收集箱是默认清单，可改名但不可删除」；⑥ 正在筛选被删清单时自动回落到「全部任务」。

- [ ] **10. 分类 CRUD 与删除联动**
  操作：「管理分类」→ 新建 / 编辑 / 删除一个已被 2 条待办使用的分类。
  预期：删除后这 2 条待办的 `category_id` 置空，在「按分类」分组下落到「未分类」；侧栏「任务分类」标题后的数字减 1；不出现悬空分类。

- [ ] **11. 悬空引用提示 🔵**
  操作：账号已上传数据后，在 Supabase Table Editor 把某条 todo 的 `list_id` 改为 `ghost`、`category_id` 改为 `ghost-c`（不增删清单/分类）；用无本地数据的浏览器登录同一账号（触发 `pull`），进入 `#/todos`。
  预期：分组切「按清单」出现「未归类（清单已删除）」，切「按分类」出现「未归类（分类已删除）」，标题为琥珀色（`orphan:true`），数据不丢、不崩溃；再做一次任意保存或刷新后，migrate 会把它们收口到收集箱/未分类。注意：不能用「改 localStorage 后刷新」造这个场景，冷启动 migrate 会直接修复。

## 五、习惯 🟢
